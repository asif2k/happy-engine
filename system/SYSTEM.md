# happy system: the creature system of the engine

One folder, no designers: every feature is an API of `engine.system` (`happy.system` in a page whose callback calls the engine `happy`), and every file the logic reads is in ONE file, `system.bin`. `engine.js` and `worker.js` are the core engine and are
not touched: the system hooks into them with the bundler's own macros. Few files on purpose: a new one only when something needs it.

**This copy (`happy_system`).** It was extracted from the `happy` repository, and its first commit is that import. Left behind in `happy`: the tests, the demo and editor pages, the node tools that wrote the data and the creature files (`build.js`, the importers, `vehicles.js`, `spiders.js` ...), and the modular kits (`kit_*.js`, `buildings.js`, `facade.js`, `scatter.js`, `locations.js`). A path below that is not in this folder is in `happy`; those parts of this record describe things that are not here.

## The pack (`system.bin`)

Header (JSON), then one gzip blob a section, so a page unzips only what it asks for. A `tree` section is a JSON tree where every array of numbers (a track, a list of harmonics) is cut out and written as whole numbers (`0.224` = 224 at 3 decimals)
as differences, one varint each; the text keeps `[]` in its place. It is lossless: a number that would not come back as the same double stays in the text. The browser needs no library to unzip (gzip, `DecompressionStream`); the worker uses `data.js` as it is.

```js
engine.system.load("/system/system.bin").then(function (system) {
  return system.use({ gaits: ["people"], actions: ["designed_basic"] });   // the styles into the page's registry; the worker reads the same sections ITSELF
}).then(function () { const sp = system.species(def); ... });
```

**LOAD ALL: the whole system in one promise.** `system.load(url, { all: true })` resolves when everything is in and nothing below it has to wait for anything: every gait style and action set in the page's registry AND in the worker's (the worker has read them itself: the promise holds until it says so),
the AI's blocks registered in the worker, the lite human's file read, the clip sets made. `system.loaded` says what it did (about 0.3 s once the pack is fetched):

```js
engine.system.load("/system/system.bin", { all: true }).then(function (system) {
  // system.loaded = { all: true, ms: 296, stages: { libraries, blocks, human, clip_sets (ms each: they run together) }, size, sections: 131, gait_libraries: 18, gait_styles: 3383,
  //                   action_sets: 27, actions: 7064, blocks: 35, human: true }
  return system.human({ model: "lite" }, { name: "person" });             // no later call reads a file or waits for the worker
});
```

A page that needs less leaves `all` out and asks for what it uses (`system.use({ gaits: [...], actions: [...] })`, then whatever it calls reads its own sections when it is first asked). A reading of the worker's that fails fails the promise (`system.worker_errors` has it too).

Sections: `gaits.<library>` and `actions.<set>` (trees), `index.gaits` (which library holds which style: a creature that names a style the page has not got is given its library), `human.model` (the lite human's file, `raw`), `blocks`, `clip_sets` and `ground.textures` (the terrain's and the roads' materials, `raw`: HGT1). The first version's file also had `human.skin`, `human.detect`, `registry`, `animals.index` and `animal.<name>`; they went with the generators, the importer and the photo-face modules that read them (the lite human is drawn from the palette without them).

`system.bin` was written by `build.js` of `happy` (`node system/build.js --gaits <folder> --actions <folder> --human <file> ...`, from the data of the first version of the system); that tool is not kept in this repo, so here the pack is data to read. Its rules still hold for what is in it: the old names are not kept (a format `<old>.gaits` is `happy.gaits`, a pointer into the old tree is the path alone), and a fitted action's description has no fit report.

## Texture maps (`system.maps`, `material.maps`)

A creature gets its detail from SMALL pictures, not from vertices: two maps, 64, 128 or 256 texels a side (any size from 8 to 1024), made from the mesh it already has. The first packs what a surface says into ONE picture, so a pixel costs two texture reads and no more:

| map | channels |
|---|---|
| `color` | R G B the colour, sRGB (the card turns it into linear light before it filters and lights it); times the mesh's vertex colours, so white vertices show the picture as it is; A is 255 |
| `pack` | **R** ambient occlusion (255 open, 0 shut), **G** roughness, **B** metal, **A** opacity (255 solid; the material's `alpha_test` cuts under it) |

`material.maps` is `{ color?, pack?, ao? }`; each picture is `{ size, data }` (or `{ width, height, data }`), `data` the bytes (RGBA, row 0 is v = 0) as a `Uint8Array` or as BASE64 text (a creature file is text: `system.maps.text(maps)` makes it). A species with no maps has the shader it always had; one with a `pack` pays one texture read and the shader has no `if` and no ternary (every line is arithmetic). The packed map REPLACES the species' roughness and metal (as the engine's own maps do) and the vertex channel (a part's own roughness, the eyes) still mixes its values over it. The occlusion goes two ways, `ao: [ambient, colour]` (default `[1, 0.5]`): to the ambient light (`mat.ao`: the forward pass) and to the colour (both passes: the deferred pass has no occlusion of its own). `sp.set_maps(maps | null)` gives a species other maps.

**Making them** (`system.maps`, also a pure module for tools): `apply(def, { size })` gives the definition with its mesh unwrapped and its material given the maps (the given one is not changed); `make(mesh, opts)` is the same for a mesh; `unwrap(mesh, { size, pad, cone })` and `bake(mesh, { size, roughness, metal, ao, sampler })` are its two halves.

* the UNWRAP groups the triangles in CHARTS (patches that face about one way: within `cone`, 70 degrees by default, of the biggest triangle's normal; the small ones join the neighbour they face most like), lays each flat along its mean normal and turns it to the tightest box, and packs the boxes in the unit square at ONE texel density, `pad` texels apart (1 up to 128, 2 above). A vertex on a seam is made again (positions, normals, colours, roughness, metallic, part ids, skin indices and weights go with it), so a creature's skinning and its variants are as they were;
* the BAKE rasterizes every triangle into the texels it holds and reads the mesh's colour and material there (`sampler(position, normal, defaults)` may say another: how an sdf's own field is read); the occlusion is counted by rays over each texel's hemisphere against the mesh itself (a grid of its triangles: 12 to 24 rays, a radius of 0.15 of the creature's size); the texels no chart holds are filled outwards, so that a filter or a mip never reads a hole. The vertex colours of the new mesh are white: the picture has the colour now;
* it is deterministic (the same mesh gives the same bytes). Measured: the 2,008 vertices of a bear are 124 charts and 2,993 vertices, 90 ms at 64 and 270 ms at 256; a small quadruped baked in the page at 128: 2,006 to 2,815 vertices, 74 ms. The two maps with their mips cost about 43 KB a species at 64, 175 KB at 128 and 700 KB at 256.

What it is not (yet): a mesh that is already coloured vertex by vertex gets those colours back in its picture, so the maps add the occlusion, the roughness, metal and opacity pictures and the room for a `sampler` (an sdf's field, a painted pattern), not detail of their own; the charts fill a third to half of the square; the occlusion is that of the bind pose; the engine's depth and shadow passes read the base colour's alpha, not the packed one, so a cut-out casts the shadow of the whole surface; the dyes of a variant still come from the vertices (the picture times the dye); a creature of the pack or of the library has to be baked (`apply`) by whoever makes it: nothing is baked on its own, except by a `texture` recipe (the next section).

### Texture on an sdf creature (`texture`, `system.maps.paint`)

A creature that is drawn from an sdf has no mesh until the mesher has made it, so there was nothing to bake. Its definition may now carry a **texture recipe**, next to its `sdf`: `texture: { size: 256, seed: 5, layers: [...] }`. `system.species` bakes it when the species is made (the sdf must have been made first, `system.build_sdf`, as for any species): the mesh the creature is drawn with (the sdf's, the tissue's carve included, or the creature's own `mesh`: a recipe works on a mesh creature too) is unwrapped and painted into a colour map and a packed map, and the species is made of that mesh (new uvs, white vertices) and `material.maps`. `sp.texture` is the report (`unwrap`, `bake`, `notes`, `layers`), `system.texture_report(def)` the same for a definition. The recipe is what a file keeps; the pictures are made again, the same bytes (every layer has a `seed`), in 70 ms at 128 and about 230 ms at 256 on the fly, and are kept for the next species of the same shape and recipe.

A layer is `{ kind, parts?, colour?, strength?, roughness?, metal?, height?, sym?, edge?, seed?, ...its own }`, and layers act in order on the colour and the material of each texel, **in the creature's own space**: a pattern is read at the texel's 3D place, so it is the same on every chart, has no seam and, with `sym` (the default), the same on both sides of the body (it is read at |x|). `parts` names the sdf parts it paints, by id or by the start of an id and `*` (`"abdomen*"`: the mesher's part of a texel is told to the sampler: the corner of its triangle it is nearest); none paints the whole creature. Colours are on the scale of the parts' own. The kinds:

| kind | its own keys | what it makes |
|---|---|---|
| `fill` | | the colour / roughness / metal everywhere on the parts: a base tint, a glossy shell |
| `stripes` | `axis`, `period`, `width`, `offset`, `wobble`, `wobble_scale` | bands across the body, a tiger's, a zebra's, a marble's veins (a large wobble) |
| `spots` | `size`, `radius`, `density`, `vary` | a leopard's, a ladybird's: a cellular pattern, a share of the cells has a spot |
| `cells` | `size`, `line`, `vary` | the lines between cells and each cell a little lighter or darker: scales, scutes, a giraffe, cracked mud, the facets of an insect's eye |
| `gradient` | `by` ("position" or "normal"), `axis`, `from`, `to` | a pale belly, a dark back, a bleached tail |
| `noise` | `scale`, `octaves`, `amount`, `threshold` | brightens and darkens (mottling, dirt); with a colour, patches of it (camouflage) |

A number out of its range is held to it and said, a layer that is not one is left out and said (`notes`, also `console.warn`: a creature is made of whatever it is given). `system.maps.painter(spec)` is the sampler alone (for a bake of your own), `paint(mesh, spec)` the unwrap and the bake in one call, `clean_texture(spec)` the recipe as it is taken. **What it cannot do**: the detail is limited by the atlas, whose charts fill a third to half of the square at one texel density (the fly at 256 is 4 mm a texel, a facet of its eye needs 3: use 512 or bigger facets); the colour between two parts is still the vertices' (blended over a few millimetres), only the recipe's patterns are crisp; and a variant's dye multiplies the picture. The fly of `creatures/fly.js` carries one (the stripes of its thorax, the bloom of its abdomen, the facets of its eyes, the veins of its wings).

**Relief: a normal map (`height`, `bulge`, `step`, `normal`).** A colour that is only painted is flat: the light does not find the cracks between stones. A layer may say a `height` (metres, -0.5 to 0.5): where the layer is, it raises the surface by that much, a minus sinks it. `cells` with `height: -0.04` are cracks of 4 cm between blocks, `stripes` with `height: 0.004` the ribs of a corduroy or of wound linen, `spots` bumps or pits, `gradient` a ridge or a step, and a `noise` with no colour is grain (from minus the height to plus it). `cells` have two more: `bulge` (a block is a dome, that much higher in the middle of its cell) and `step` (every block at a level of its own, plus or minus `step`). A layer of relief alone needs no colour. The heights are in the layers' order and add up; `strength` of a layer weighs them as it weighs its paint.

A recipe with any height bakes a THIRD picture, `material.maps.normal` (512 x 512 for the stone golem: `creatures/stone_golem.js`): a tangent-space normal map of that height field, `(x, y, z) * 0.5 + 0.5` with x along u and y along v of the uvs (flat is 128, 128, 255). The slope is measured on the surface, half a texel each way along the directions u and v go in, by calling the height where the texel is (so it does not depend on the size of the picture or on the unwrap), and the occlusion of the packed map is darker where the surface is low (`normal: { strength: 1, cavity: 0.6 }`: how steep the slopes read, 0 to 4, and how much darker the low parts are, 0 to 1; `normal: false` leaves the map out). A recipe with no height makes no normal map: every creature of the folder that had a texture is as it was. The species' shader reads it (`MAT_NORMAL_CODE`, species.js): the normal of the pixel is turned by it in the frame of the uvs made from the derivatives of the WORLD POSITION and of the uv (no tangents in the mesh; exact at any angle), first in `happy_material`, so the specular antialiasing that follows widens the glint by how much the turned normal changes across a pixel, in the forward pass and in the deferred G-buffer pass alike. The engine's own normal map (`u_normal_map`, `material.normal_map`) is a page's own picture and is not touched: it builds its frame from the derivatives of the normalized view vector, which is not exact on a surface seen at a slant. `sp.set_uniform("u_happy_normal_scale", 0.5)` takes some of the relief away at run time (1: all of it). It costs one more texture read a pixel, and the bake about 70 ms more at 128 and 1 s more at 512 (five calls of the height a texel). The picture is stored lossless like the pack (`{ size, deflate }`: a JPEG would bend every normal it holds); `check` refuses a JPEG for it.

`parts` may leave parts out: an id that starts with `!` is excluded (`["!eye*", "!lid*"]` is every part but the eyes and the lids: the golem's relief is on its stone and not on its eyes); a list of exclusions only means all the others; a mesh that has no parts is all of them.

**The maps, stored encoded.** A creature file is text and a raw map is a base64 of every byte: 700 KB for a 256 map, 175 KB at 128. A map may instead be `{ size, jpeg }` (the COLOUR: a JPEG, quality 0.88) or `{ size, deflate }` (any map, lossless: its four planes one after the other, deflated; the PACK is stored this way, never as a JPEG, because it holds the opacity and the metal and a lossy picture without alpha spoils both: `check` refuses it). `await system.maps.encode(maps, { quality })` makes the encoded maps (a browser: the canvas's JPEG and CompressionStream), `await system.maps.decode(maps)` fills `data` in place (createImageBitmap with no colour conversion, DecompressionStream) and returns them; `system.build_sdf` decodes the maps of the definitions it is given, and a species made of maps that are not decoded says to decode them. `system.maps.text(maps)` writes the encoded form when there is one. Measured on the bake of the fly at 256 (the demo's "measure" button): 699 KB as raw text, 60 KB encoded (JPEG 23 KB, pack 37 KB), 11.7 times smaller; the colour comes back at 36 dB with the biggest error on the edges of charts, the pack exactly. On a bear at 128 the colour was 175 KB (both maps) raw, 33 KB gzipped, **4.5 KB as a JPEG** at 0.85 (35.9 dB); a lossless WebP of the same was 21 KB, a PNG 35 KB. A recipe makes the pictures unnecessary for an sdf creature (they are made again from it); the encoded form is for pictures that cannot be made again (an imported or painted map, a baked animal of the library).

## Vehicles with suspension and an engine (`vehicle: { realism: true }`)

A vehicle (`vehicle: { model: "car", wheels: [...] }`) was a KINEMATIC car: a bicycle model that sets the chassis' velocity and heading, with wheel bones that follow the ground a few centimetres. The flag `realism` (or `suspension`, the same flag) makes it a DYNAMIC one, a raycast-wheel car: 
every wheel looks down at the ground under it (the terrain and the props of the physics world: `happy_floor_at`) and stands on a SPRING and a DAMPER under a sprung body; the spring's force is the wheel's load, so the weight moves between the wheels as the body dives under the brakes, squats under the throttle and rolls in a bend; 
a TYRE makes a force from its slip (the slip ratio along the wheel, the slip angle across it, a Pacejka-like curve scaled by the load and the friction and held inside the friction ellipse), so a wheel can spin, lock, slide and grip, and the car under- and oversteers by itself; a wheel is a flywheel (its inertia, the drive torque, the tyre's reaction, the brake, integrated implicitly: stable at any grip); 
an ENGINE (a torque curve against the revs, idle, a rev limiter, engine braking) drives them through a gearbox that shifts by itself (up and down by the revs, a reverse from a stop, a pause for the shift) and an open differential that is limited so that a wheel in the air does not stop the car; rolling resistance, the drag of the air, a downforce, ABS.

```js
vehicle: { model: "car", wheels: [{ bone: "wheel_f_l", drive: 1, steer: 1 }, ...], top_speed: 50, max_steer: 0.55, steer_speed: 28, travel: 0.12,
  realism: true }                                  // everything has a default worked out from the mass (the physics section's), the top speed and the wheels
  realism: { mass: 1450, cg: 0.52,                 // kg, the centre of gravity's height (m)
    suspension: { hz: 1.3, damping: 0.35, bar: 0, bump: 12 },                 // the body's bounce (Hz), the share of critical damping, an anti-roll bar (N m / rad: 0 the springs' own), the bump stop's stiffness over the spring's
    engine: { power: 105, idle: 800, redline: 6500, torque: 214, inertia: 0.25, brake: 19, curve: [[rpm, N m] ...] },   // kW or the peak torque, or a curve of up to 8 points
    gearbox: { ratios: [3.5, 2.4, ...], reverse: 3.4, final: 4.8, up: 5500, down: 2600, time: 0.22, efficiency: 0.9 },    // up and down are the revs at which it shifts, time the pause (s)
    tyres: { grip: 1.05, grip_long, grip_lat, stiff_long: 16, stiff_lat: 18, rolling: 0.013, inertia: 1.2 },  brakes: { torque, hand, abs: true },  aero: { drag: 0.45, downforce: 0 },  diff: 0.3 }
```

The compile (`body.js`, `compile_realism`) turns that into 64 numbers after the rollover's four in the vehicle section (flag bit 1); the model is `happy_vehicle_real_step` (world.cpp): up to 16 sub-steps of 1/240 s a frame, planar motion (the speed along the nose and across it, the yaw rate) plus the sprung body's heave, pitch and roll. The body mover still owns the root: it moves it by the velocity, keeps it on the ground and the walls act on it, and the next frame starts from the velocity that is left. 
The chassis is drawn leaning by the plane through the contacts plus the sprung body's own pitch and roll (the `lean` column), the wheels spin with their real speed, steer by their real angle and follow the ground in the suspension's travel. **What it is not**: a full six degree of freedom rigid body. The root keeps its own height (a jump or a ramp is the body mover's, not a physical flight), the heave is not drawn (the body does not rise over a bump, the wheels move under it), and the rollover is still the planar model of world.cpp. 
It costs about four sub-steps of the tyre model of every wheel a frame, for the vehicles that are near.

**What the page reads.** `sp.vehicle_state(c)` -> `{ rpm, gear (-1 reverse, 0 neutral), throttle, brake, spinning, locked, sliding, airborne, speed (m/s along the nose), lateral (across it), pitch / roll (rad, + nose down, + the left side up), yaw_rate, heave, sim (the worker's seconds), age }`, ten times a second from three events (`HAPPY_EV_VEHICLE` 14, `_MOTION` 15, `_BODY` 16, `_TIME` 17), and `system.on_vehicle(sp, c, state)` as each comes. 
The driver's controls are the kinematic car's: `sp.set_controls(c, { throttle (- is reverse from a stop), brake, steer (+ turns to the left), handbrake })`.

**The cars** (the creature files `sedan.js`, `pickup.js` and `sports_car.js` of `creatures/`; their writer, `vehicles.js`, stayed in `happy`): `sedan` (4.6 m, 1,450 kg, front wheel drive, 105 kW, four doors, four seats), `pickup` (5.3 m, 2,150 kg, four wheel drive, a diesel with 520 N m, soft long springs, two doors, a bed), `sports_car` (4.4 m, 1,380 kg, rear wheel drive, 330 kW, six gears, a wing that presses it down, stiff springs). 
Each is an sdf with a HOLLOW body (the arches of the wheels, the cabin and the openings of the doors are cut out of a tub), DOORS that are bones hinged at their front edge (`doors`: `system.enter` walks a person to the door, the door opens, the person sits with its feet on the pedals and its hands on the wheel; `system.leave` gets it out), SEATS (`seats`), a steering wheel that is a bone of its own (the `steering` entry of `doors` is the axis it turns about) and no glass in the side windows, so that the people in it are seen. 
Measured in the demo (the worker's own seconds): the sedan 0-100 km/h in 11 s, about 180 km/h at the top, 100-0 in 42 m with ABS and 1 g across; the pickup 8.2 s, 4.9 degrees of dive and 6 of roll in a bend; the sports car 5.0 s (a third of it in wheelspin), 290 km/h, 100-0 in 36 m. The AI drives them: in a hosted world (`?world=1&cars=sedan,pickup`) their minds (`walk`, `avoid`, `drive`, `wander`) say the same controls as a driver.

**A car that looks like a car: `hatchback`** (`creatures/hatchback.js`; its writer, `hatchback.js`, stayed in `happy`). The sdf cars above are boxes of an sdf (the sedan draws about 37,000 triangles and still looks like a toy), so this one is built the way a game car is: a LOW POLY MESH and the detail in pictures. 4.26 m, 1,290 kg, front wheel drive, four doors, four seats, the same physics, doors, seats and steering wheel as the sedan (it drives the same: 0-100 km/h is the engine's, the page's controls are unchanged).
* THE MESH (4,796 vertices, 4,358 triangles, `body.mesh`, no `sdf`): the body is a LOFT of its cross sections along its length (nose, hood, windscreen, roof, hatch; each station is eight points from the middle of the belly out over the shoulder to the middle of the roof, read from tables of the car's own numbers: belt line, roof line, widths, belly), with the wheel arches CUT IN THE STATIONS (the opening's edge is a half circle round the hub, stations every 18 degrees), and a tunnel and an inner wall above each wheel. The DOORS are the shell's own quads between the stations that are the doors' edges, on their hinge bones (so a door fits its opening exactly and swings about its front edge); a LINER (the shell's rings drawn inward, 4.5 cm in) is the cabin's inside, the headliner, the door cards (on the door bones) and the firewall; a floor, four seats, the dash and a steering wheel (a torus on its own bone) are boxes; the wheels are lathes (a tyre of 205/55 R16 with a profile, a dished rim, a barrel and a brake disc behind it). Every vertex has ONE bone (`skin_count: 1`).
* THE PICTURES (one 1024 atlas: colour, packed map, normal map, stored deflated in the file, 1 MB in all): painted by `maps.bake` with the PAINTER of the tool as its sampler, which reads the car's own coordinates, so the grille, the lamps, the window frames, the door lines, the handles, the plate, the badge, the arch trim, the sill are where they are on a car and the same in every chart. The OPACITY plane cuts the windows (the glass is not drawn: the cabin, the seats and the driver are seen through it, and a black frame and a frit round each window are painted) and the gaps between the spokes of the rims (`material.alpha_test`); the normal map has the panel gaps, the handles, the grille's slats and the character line down the side (a ridge with its shadow under it). The atlas has its OWN SYMMETRIC LAYOUT instead of `maps.unwrap`: charts by the face's dominant axis (side, top, front, rear, the cabin's, the wheel's face, the tyre's tread) read at |x|, so the right side of the car is the left side's texels the other way (twice the texels for the same square), the plain parts (underside, brake disc, seats, ...) are 8 texel patches, and the shelf packer shrinks the scale till all fits. 4 mm a texel on the body, 4 on the wheel's face.
* THE GLASS is in the shell's own surface: where a window is, the opacity map says 0.30 (and 1.0 in a 3 cm frit round it, painted black), the tint is in the colour map, and `material.translucent: 0.99` tells the species that a pixel under 0.99 is glass (4,358 triangles, no mesh of its own: the first version had 188 more, copies of the window quads, the writer in `happy` still makes it with `--glass mesh`). Where the glass is drawn is the page's choice (below).
* WHAT IT TAUGHT: the bake writes an opacity of 255 and its sampler cannot say another, so the tool bakes twice (the second pass paints the opacity as a grey and keeps its red); `render()` in the tool is a small software rasteriser that shows the atlas and the car (PNG, no browser) in 7 s, the engine's own render took minutes; the demo's page is dark, a silver car shows panel lines that a dark blue one hides.

## Transparent surfaces (`screen.transparent`, `system.transparent`, `material.translucent`)

A deferred pass holds ONE surface a pixel and lights it once, so glass cannot be in the G-buffer. A transparent surface is lit by its OWN fragment shader (the pass's own sun, shadows, ambient, sky and air) and blended over the lit image. The engine part is `screen.transparent` of `engine.deffered_rendering` (deffered_rendering_v2.js, "TRANSPARENT SURFACES"), which has two modes, `screen.transparent.mode`:

* **`"target"` (the default): the transparent target.** The glass is drawn into ONE extra target (RGBA8: the premultiplied lit colour and the coverage, 8 MB at 1080p, filled only on a frame that drew glass) that SHARES THE G-BUFFER'S DEPTH TEXTURE (the same GL texture attached to a second framebuffer as its depth buffer, never sampled: no feedback loop), right after the G-buffer pass. The **hardware depth test** hides what is behind a wall, a frame or a person, and with the depth write on **the nearest glass of a pixel wins, whatever the order** (a farther one drawn after it is rejected, a nearer one drawn after it blends over: the order is never wrong, so instances of one species, species and cars need no sorting). The target is then blended over the lit image (ONE, ONE_MINUS_SRC_ALPHA) BEFORE the antialiasing, so TAA and FXAA see the glass as part of the picture.
* **`"forward"`: after the antialiasing.** The glass is drawn on the resolved canvas (no depth buffer there), the G-buffer's own position is the depth test (in the shader), the items that have a `distance()` far to near. No extra target; the glass is clean of TAA's jitter. (The first version.)

* `screen.transparent.material(base, { cut })` makes the transparent material of an engine pbr material (a species', a plain one; cached on `base`, one for each mode): the surface's own lighting with **the sun** (its light through the air with `ENABLE_ATMOSPHERE`, the cascades' **shadow** with `ENABLE_SHADOWS`), the **ambient** light, **the sky mirrored by Fresnel** (the atmosphere toward the reflected ray, or `screen.transparent.environment` when there is none; `screen.transparent.reflection` scales it) and **the air between it and the camera**; tone mapped and gamma corrected as the lit image is. The glass is the material's opacity (base colour alpha x the map's x the vertex's): under 0.004 nothing is drawn, and from `cut` on (when given) the pixel is SOLID and is not drawn here. `u_alpha_test` is off in it.
* `screen.transparent.add(item)` / `.remove(item)`: `item = { render(), distance()? }`, `render()` puts the draws (`engine.render_item` with the transparent material) in the command stream; the items that have a `distance()` are drawn far to near, after the ones that have none (in `"target"` mode the depth decides inside a pixel; the order only matters for a layer behind a layer). `screen.transparent.drawn` is how many items were drawn last frame.
* The shader is the lighting pass's own steps 5 to 8 for ONE surface (the same chunks, the same FL sliders and cascade uniforms: AMBIENT_SCALE, SHADOW_*, AERIAL_SCALE, EXPOSURE move it with the rest). Not in it: the moon, the water, the emissive buffer, refraction (what is behind shows by the blend: no bending). A transparent surface casts no shadow (the shadow pass draws what is solid).
* **One layer a pixel** is the price of no sorting: glass behind glass is lost when the nearer was drawn first (the far window of a car is a back face anyway: the glass is single sided). Smoke or many panes need more layers (weighted blended OIT, not here).

**Marking glass by the opacity map (`material.translucent`).** `translucent: 0.99` in a species' material is the opacity from which a pixel is solid. The species is drawn twice from the SAME triangles: in the G-buffer pass `u_alpha_test` (set to it) leaves out every pixel under it, in the transparent pass the material leaves out every pixel from it on (and under 0.004), so each pixel is in exactly one of the two; the pack's alpha (maps.js) says which. No second mesh, no `glass_from`: a window is a part of the body's surface painted 0.30, a grille, a fence or the edge of a spoke (bilinear texels between 0 and 1) show as glass-like fractions too. A pixel of 0 is a hole, as before. The whole mesh is drawn a second time (4.4k triangles for the hatchback: nothing), so give it only to a species that has translucent texels.

**A species with a glass mesh of its own** (`mesh.glass_from`, a whole number: the triangles from it to the end are glass; `--glass mesh` of the hatchback) still works: `sp.render()` draws only the triangles before it, the transparent pass the others.

**Where it is drawn is the page's choice** (`system.transparent(choice)`, returns what is chosen): a deferred pass (`system.transparent(screen)`: a species with glass is drawn by `screen.transparent`, one instanced draw, with the transparent material made from its own: bones, maps, culling and variants all work), `"forward"` for a forward page (`system.render_all` draws the glass of a `glass_from` species after every opaque thing, blended, hardware depth test, no depth write; a species marked with `translucent` shows its windows as holes there), `null` (the default): no glass, the windows are the holes of the opaque mesh.

**What it taught.** A transparent material that turns the depth write off leaves it off for the next frame's `gl.clear`, which then leaves the old depth: the first frame is right and every one after is black. `CMD_CLEAR` (rendering.js) now opens the depth and colour masks first. A shader that a material `shader:` adds is split at the end of its `void vertex()`: what is above it is the VERTEX stage's, so the uniforms of the fragment go below it. A page that draws its cars from its own `engine.on_frame` instead of the scene's passes draws them forward, over the lit image, and every test of the glass passes by accident: the cars must be drawn in `scene.on_render_pass` and `scene.on_shadow_pass`. Checked in a browser: both modes and the variants of the shader (with and without the atmosphere and the shadows), TAA, FXAA, none, two cars (the near car's body hides the far car's glass), the driver seen through the glass, the doors open.

## The human (`system.human`)

A person is the lite human: a few sliders (gender, age, muscle, weight, height, three races, and the face, the build, the bust, the soft volumes ...), a body of about 8,000 triangles with its own hands and feet, a skeleton of 39 bones, clothes and hair cut from its own
surface, a dice that mutates it. Nothing of any other human system is in it, in code or in data: it is made from ONE file (the pack's `human.model`), and drawn from the pack's base skin when its `human` says `skin` (the next section).

```js
system.human({ model: "lite", shape: {...}, look: {...}, wear: ..., hair: ... }, { name: "person" }).then(function (def) { const sp = system.species(def); ... });   // a definition of a creature, the human's own
system.species({ name: "guard", human: { ... }, legs: {...}, ... })    // a hand-written creature that HAS a `human` part: its skeleton, rig, roles, legs and mesh are the person's, its own keys come over them
```

`system.human_creature(input)` / `system.build_human(x)` (asynchronous: the file is read the first time), `human_info(def)` (height, leg, vertices ...), `human_mutation(def)`, and the modules for the tools that make people: `system.human_lite` (sliders, shape, look),
`human_lite_wear`, `human_lite_hair`, `human_lite_mutate`, `human_lite_look`, `human_lite_parts`, `human_lite_people` (the people as data), `human_lite_model()` (the file, read). `model` may be left out. The styles a person walks with are looked up in the pack's index.
A creature definition whose `human` part is a lite human is a person: a hand-written creature file and a crowd use the same one. The person is drawn from the palette: the picture skin (`def.skin`) and the face warp (`def.face_warp`) need modules that are not in this repo, and a definition that asks for them is told so (`notes`) and gets the palette.
**How a person walks.** Three things are the human's own in the gait, and each was measured on the real engine (the gait demo of `happy`, a person walking in place; a style's recorded cadence against the cadence it is played at):
* *the reach of its legs* (`happy_legs_probe`, body.cpp): a creature with two legs and feet that roll is probed with the hips at their lowest in a step and with a share of the foot's own length (`HAPPY_LEGS_ROLL_REACH`, 0.25) added to the reach forward and back. Probed for a flat foot at the ride height, the reach held a recorded walk of 100 steps a minute to half its step (200 a minute: a run). The share is a trade: the more of it, the longer the step and the further the hips have to dip to put the foot there (a step of 0.72 m dips 7.4 cm and the body thumps; 0.65 m dips 5.8 cm). Creatures with no feet tables (birds, dinosaurs, animals) are probed as before.
* *the spread of its feet* (`stance` 0.35 in `human.js`): the bind pose stands the feet 38 cm apart, a person's land 8 to 15 cm apart.
* *its two hands* (`kernel.js`, `arm_fix`): the hands a style records are of an actor whose arms are not alike and swing wider than a walk's. When the two hands differ by under `ARM_PAIR` of an arm's length (one against the other half a cycle on) they are made one arm, the mean of the two (a phone call, a handbag, a suitcase keep their own: 414 of the 1,303 styles with hands); and the fore and aft swing of a hand is held to `ARM_CAP` of an arm's length at 1.5 leg lengths a second, more as the style goes faster.
* *its standing and its walking height* (`RIDE_STRETCH` 0.995 and `CROUCH_SHARE` 0.084 in `human.js`): a person stands with its legs nearly straight (a knee bent 11 degrees where it was 40) and the gait sinks the hips by the crouch as it goes faster, so that the walk keeps the height it had. The walk's own knees (37 degrees in the middle of a stance) are a measured trade: every 0.02 more of the ride straightens them by 6 to 8 degrees and costs 6 to 8 steps a minute of cadence and 6 to 10 points of double support (a shuffle: the reach at the floor of a straight leg is short, and the rig's measured reach falls from 0.42 to 0.28 m for 5 cm more of height); more solver iterations for the probe, an earlier drag test and a limit from the landing spot did not change it. A style recorded at a lower hip height (`person_walk_cautious`, a ride of 0.977) still stands about 28 degrees bent.
* *the turn of its pelvis and its shoulders* (`kernel.js`, `yaw_fix`): the pelvis' yaw is held to 9.5 degrees in all (the recording's is 15) and the spine's yaw is made the pelvis' reversed, 1.6 times as big, so the shoulders turn 0.6 of the pelvis' turn the other way (5.8 degrees against the pelvis' 9.7; they were 4, in step with it half the time).
* *the pelvis over the foot that stands* (`body.cpp`, `HAPPY_SWAY_SHARE`): the hips move 2.1 cm each way toward the leg that carries, in the life's gait coupling: the pelvis' x was 0.000 on every frame.
* *no two strides alike* (`body.cpp`, `HAPPY_LEGS_VARY`): the stride of a person is the gait's times a number from -4.5 % to +4.5 % that is new at every cycle (a generator seeded at the spawn); it is applied after the reach's cap, which keeps 5 % in hand for it. At 30 % it shows in the measure as a step length that varies 19 % where it was 7; at 4.5 % it is under what the measure can see.
Known: there is still no variation of the arms and of the bob from one cycle to the next, and the walk's knees are as above.


## The world and the AI (`system.world`, `system.ai`)

A creature that lives in a world has a MIND: a tree of BLOCKS (behaviours: health, needs, wander, flee, walk, avoid, gunner, drive, fly, fight, use ...) that its worker function loads by name. The 35 blocks are texts in the pack (ES5: the worker runs each as the body of a function); a world is a program
(a JS text given a builder `w`: `w.bounds`, `w.ground`, `w.nav`, `w.zone`, `w.add("chair", { pos, yaw })`, `w.spawn({ family, zones, cap })` ...) that the host makes live: the engine's physics bodies, the navigation map the worker bakes, the creatures it is given, the runtime's tick.

```js
const host = system.world({ tolerant: true });
host.load({ world_text: "w.ground({ y: 0 }); w.nav({ agents: {} }); ... return { name: 'the yard' };", creatures: { civilian: u.file }, gaits: ["people"], actions: ["designed_basic"] }).then(function () {
  host.start(); const h = host.spawn("unit_civilian_5", -10, 0, -10, 0);       // then, every frame: host.update(dt); host.where(h) ...
});
system.ai.blocks() / names() / sets() / use(names | "all") / clip_sets()   // the pack's blocks, the ready-made minds, the clips a block needs by species and pack; use registers blocks in the worker (the host does it)
```

A creature file carries its mind (`mind`: the blocks it lives by, with numbers scaled to its size): a civilian wanders, gets tired and hungry, flees; a rifleman holds his post and fires at what he sees.

## A creature's own function (styles and actions made at run time)

A definition may carry `worker: function (api) { ...; return { spawn, think, on: { end } }; }`. The page sends its SOURCE to the worker (a function cannot cross), so it must be self-contained: it takes everything it uses from `api`. It runs once for the species, and its hooks run every frame for every
living instance, before the system's own frame. State of the instances lives in columns (`api.f32()`, `api.i32().fill(-1)`, `api.u8()`), indexed by `me.slot`, never in `me` (one shared object whose slot moves). The person demo is the example:

```js
const def = Object.assign({}, u.def, { max_instances: 1, worker: function (api) {
  var STROLL = api.style({ base: "person_walk", tweaks: { stride: -15, hip_sway: 25, arm_swing: -25, bounce: -20 } });     // a gait STYLE made from numbers: the plain walk with the easy sliders turned (percent), in a SPARE gait slot
  var JOG = api.style({ base: "person_walk", blend: { run: 30 }, tweaks: { stride: 20, lean: 20 } });                       // blend: the share of another style (for two legs: run, shuffle, stomp, strong, strut)
  var WAVE = api.action("wave"), BOW = api.action("bow");                                                                  // actions of the library, by name (system.use / load all put them in the worker)
  return { think: function (me, dt) { if (me.acting() >= 0) return; me.style(JOG, 0.6); me.go(0, 2.6); },                  // me.style(h, seconds): the gait changes over that time
           on: { end: function (me, how) { me.say(api.tag("done"), how); } } };                                           // me.say(tag, v) comes back to the page as sp.on_worker_event(slot, gen, tag, v)
} });
def.legs = Object.assign({}, def.legs, { slots: 3 });                                                                      // the spare gait slots a creature makes its styles in are asked for in its definition
```

**Gaits and actions IN the creature file** (`creatures/transformer.js` is the example: a giant robot that reads nothing of the libraries; the spiders of `creatures/` are the second, on eight legs). The body of the file carries `gaits: [...]` and `actions: [...]` (the definition's own keys: the worker makes them before its function runs, so `api.style("tf_walk")`, `api.action("tf_punch")` and a block's `gait: "tf_run"` / `clip_attack: "tf_punch"` find them like a library's; a creature's own name begins with the creature's, the name of a library's is refused). A gait is a whole style in the form of the libraries (`speed`, `stride`, `step_height` in leg lengths, `bob`, `swing`, `cycle`, `phase`, the foot's `path`, and `upper`: what the hips, the spine, the head and the hands do over a cycle); the legs' own first gait (`legs.gait`) is the same style in metres, so a host that never puts a style on the creature still sees it walk so (the file computes it from the style), and `legs.slots` leaves the spare gaits the two styles are put on. An action is a whole spec in the form of the libraries (phases, tracks of the roles' numbers, events `emit` / `impulse` / `hit`): the numbers are creature independent, so the weight of a body is in the times, and `height` of a jump is in hips' heights. A page puts the file's styles into its registry (`system.gaits.add`) to use them with `sp.set_style`; the creature demo does.

`me.go(vx, vz)` wishes a velocity, `me.stop()` none, `me.act(h)` plays an action (the demo calls `me.stop()` first: the person stands while it plays), `me.acting()` is the handle of the one playing or -1, `me.x / me.z` where it is, `me.rand()`. `api.style` and `api.action` throw for a name that is not in a loaded library (`load all` has them all).
An action's ending is `on.end(me, how)`: 0 it finished, 1 stopped, 2 gone, 3 replaced. A creature may also have a behaviour tree (`ai`) and blocks (see the AI above); a creature file may carry its own mind.

**Eight legs** (`creatures/spider.js` and the other six spiders, written by `spiders.js` of `happy`). The legs of a creature go to eight (`HAPPY_MAX_LEGS`); the pattern `alternate` steps the legs 1 and 3 of one side and 2 and 4 of the other together, then the other four, so four feet are always down: the alternating tetrapod of a real spider, measured on the real engine in all seven bodies and in each of their three styles (the fore and aft place of the eight ankles over the cycle: the legs of a set correlate by 0.93 to 1.00, the two sets by -0.69 to -0.89, in all 21 of them, and the body holds its height to under two centimetres). The libraries have no style of eight legs: a style's `phase` names six limbs (`fl fr ml mr hl hr`), so a creature of eight legs is given the pattern's order and the style's numbers (a file's own styles say `pattern: "alternate"`). The tracks of an action can name the front legs (`legf_l`, `legf_r`) and the hind ones (`leg_l`, `leg_r`) and no others: the four legs of the middle go on stepping while the front ones rear or reach, and the pair of fangs is the `jaw` role (`axis`, `mirror`: two fangs that open apart; `jaw.open` in an action) and the abdomen the `tail` role. Two limits that the compile reports only when a creature is made: a species takes three dyes at most, and a dye must cover a vertex (a ball at a knee smaller than the leg it sits on is swallowed by it and its dye finds nothing). The creature demo lists the styles of a creature's own first, whatever the number of its legs.

## What is in the system, and what is not

In: the whole logic of a creature (the rig and its solvers, the gait, the body, the life, the face, flight, wheels and vehicles, aircraft, the physics proxy, the ragdoll, hit zones, hands and grips, props, particles, the mind in the worker: behaviour trees, goals, blocks, the world service),
the world and its host, the mesher, the lite human, the gait libraries, the action sets, the AI's blocks and clip sets.
Not in it: designers, labs, studios, the AI and world editors and demo pages; the hand-made creature files and the scenes of the first version's worlds (a world is a program you give the host); any other human system (there is one human, the lite one); the glb part catalog; the tools that made its data.

Names that changed with the port: the page's object is `engine.system`; a definition's part key is `system` (it was the old name); the worker's functions and constants are `happy_*` / `HAPPY_*` / `CMD_HAPPY_*`; the data formats are
`happy.gaits`, `happy.actions`, `happy.human_lite`, `happy.animal_library`, `system-world` ...; the piece files (`.happypart`, a new format: the old ones are not read) begin `HSYSPART` and their mesh packs `HSYSMPK1`.

## How it is checked

The tests stayed in `happy` and are not kept here: the data's tests (`test.js`, with `--page` a real browser), the tests of the pure modules (`test_*.js`) and the first version's own suites, run against this port by a mirror tool (the C++ of the worker, 173,000 checks; the JS, 11,829). The figures in this record are theirs. A change here has to be tried in `happy`, or with new tests.
